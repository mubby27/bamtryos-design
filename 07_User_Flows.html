System Interaction Flow
1
UserOpens app, taps "Get Started"
App checks for existing keystore on device. If found, routes to sign-in. First-run proceeds to DID creation.
2
Bridge AppGenerates 12-word BIP-39 mnemonic locally on device
Mnemonic is generated inside the Bridge App using a cryptographically secure random number generator. It never leaves the device and is never sent to the Cloud OS.
Security: CSPRNG with 128 bits of entropy → 2048-word BIP-39 dictionary → 12-word phrase (local only)
3
UserSets 6-digit PIN and confirms mnemonic backup
User sets PIN, writes down mnemonic, and confirms 3 random words. App won't proceed until confirmation passes — this is the only recovery path.
4
TEE KeystoreMaster seed encrypted and stored in hardware-backed secure storage
Mnemonic → BIP-39 seed → encrypted with AES-256-GCM using PIN-derived key → stored in Android Keystore / iOS Secure Enclave / Windows TPM.
The mnemonic is cleared from RAM immediately after storage. PIN is never stored.
5
Bridge AppDerives chain keypairs locally → sends DID Document to Cloud OS for registration
BIP-44 derivation paths produce ETH, SOL, ATOM addresses inside the Bridge App TEE. DID Document is assembled (W3C DID Core 1.0) and sent to the Cloud OS Identity Module for permanent registration. The private keys never leave the Bridge App.
did:bamtry created (Bridge App)DID registered in Cloud OS
6
Cloud OSCloud OS Storage Module pins DID Document to IPFS, anchors CID on-chain
The Cloud OS Identity Module routes the DID Document to IPFS via Bamtry's pinning gateway. The returned CID is submitted to the DIDRegistry smart contract. The identity now lives permanently in the decentralised Cloud OS runtime — not on any device.
IPFS CID returnedOn-chain tx via Cloud OSIdentity: Cloud OS owned
7
UserSelects active chains → Arrives at Dashboard
User activates desired chains (Ethereum, Polygon, Solana, Cosmos). Wallet service fetches initial balances. Onboarding is complete.
Total onboarding time target: under 3 minutes
✓ Happy Path
  • 1User taps Get Started
  • 2Mnemonic shown, user writes it down
  • 33-word verify passes first try
  • 4PIN set successfully
  • 5Keys stored in TEE
  • 6DID created and pinned
  • 7Dashboard loaded, balance shown
✗ Error States
  • !PIN confirm mismatch → show inline error, re-enter
  • !Word verify fails → "Try again" (max 3 attempts, then re-show phrase)
  • !TEE unavailable → warn user, offer software fallback
  • !IPFS pin fails → retry 3×, store locally and sync when online
  • !Network offline → DID creation completes locally, chain registration deferred
02
Send Transaction
User sends native tokens or ERC-20 / SPL tokens to any address on any supported chain
Critical Path Core Feature
Transaction Send Flow
1
UserOpens Send screen, selects chain and token
User selects source chain (e.g. Ethereum), token (ETH or ERC-20), enters recipient address and amount.
2
Cloud OSTransaction Module validates address + AI risk screen
The Bridge App sends the transaction intent to the Cloud OS Transaction Module. Address checksum and format are validated server-side. The AI Agent (Cloud OS) screens for known scam patterns, contract audit status, and anomalous parameters.
Address checksum ✓AI risk score: Cloud OS
3
Cloud OSTransaction Module builds, simulates, and estimates fee
The Cloud OS Transaction Module builds the unsigned transaction and runs a simulation against a fork of the target chain to confirm it won't revert. Fee estimate is normalised and returned to the Bridge App for display. Orchestration logic lives entirely in the Cloud OS.
Fee: 0.0005 ETH (~$1.50)Simulation: Cloud OS
4
UserReviews confirmation screen and approves
User sees: recipient, amount, estimated fee, AI risk score badge. If risk score is HIGH or CRITICAL, a prominent warning is shown. User taps "Confirm & Send".
5
TEEPIN / biometric auth → private key signs transaction
User enters 6-digit PIN or uses biometrics. TEE decrypts the master seed, derives the signing key for the selected chain, signs the transaction, and returns only the signed bytes — the key never leaves the TEE.
6
Cloud OSTransaction Module receives signed bytes, broadcasts to network
The Bridge App returns only the signed bytes to the Cloud OS — the private key never left the Bridge App TEE. The Cloud OS Transaction Module broadcasts via RPC (Infura/Alchemy for EVM, QuickNode for Solana). TxHash returned to Bridge App for display.
TxHash: 0xabc…Status: PendingKey stayed in Bridge App
7
Cloud OSCloud OS pushes real-time confirmation updates to Bridge App via WebSocket
Cloud OS invalidates the balance cache. WebSocket pushes transaction:update events to the Bridge App as confirmations accumulate. Bridge App renders the activity feed and notification update.
EVM: 12 confirmations = final. Solana: 1 confirmation. Cosmos: 1 block.

1
UserOpens Storage screen, taps Upload
User selects file from local device storage. File picker shows type and size. Files over 100MB are rejected with a clear error message.
2
Bridge AppFile encrypted inside Bridge App — plaintext never leaves the device
The Bridge App derives an AES-256-GCM encryption key from the DID's key material (via TEE). File is encrypted entirely within the Bridge App — plaintext never reaches the Cloud OS or IPFS. Only ciphertext is transmitted.
Key derivation: HKDF-SHA256Cipher: AES-256-GCMPlaintext: Bridge App only
3
Cloud OSStorage Module receives ciphertext, pins to IPFS
Encrypted bytes are streamed from the Bridge App to the Cloud OS Storage Module via multipart upload. The Cloud OS routes ciphertext to Bamtry's IPFS pinning node — it never sees the plaintext. Progress callbacks update the Bridge App UI in real-time.
Upload shows real-time progress bar (0–100%)
4
Cloud OSStorage Module saves CID and metadata — access scoped to owner DID
CID, file name, MIME type, size, and tags are saved in the Cloud OS storage_files table. Access control list is initialised with the owner's DID. Apps are granted scoped access, not ownership.
5
UserFile appears in Storage list with CID and size
Storage screen updates to show the new file. User can share the CID, grant access to other DIDs, or set an expiry on the access grant.
04
AI Agent Chat → Transaction Execution
User asks the AI agent to perform an on-chain action via natural language — agent proposes, user confirms
AI FeatureSafety Critical
Agent Interaction Flow — "Swap 0.1 ETH to USDC"
1
UserTypes: "Swap 0.1 ETH to USDC on Uniswap"
Message sent to /agent/chat endpoint. Session ID created for this conversation thread.
2
AI Agent (LangChain)Intent parsed, context retrieved from Pinecone + FAISS
LangChain parses the intent as a DEX swap. Relevant context retrieved: current ETH/USDC price, user's ETH balance on Ethereum, Uniswap v3 contract ABI from vector store.
Intent: DEX_SWAPContext: balance + price
3
GPT-4oGenerates action proposal and human-readable explanation
GPT-4o produces the action JSON (TRANSACTION_PROPOSAL) and a plain-English summary. Response streaming enabled — user sees text appear in real-time.
4
Cloud OSCloud OS sends action card to Bridge App for rendering
The Cloud OS AI Module sends a structured TRANSACTION_PROPOSAL to the Bridge App. The Bridge App renders the action card: from/to token, expected output (e.g. 300.24 USDC), estimated fee ($1.20), AI risk score (LOW, score: 8/100), and "Confirm" / "Cancel" buttons.
5
UserReviews action card and taps "Confirm"
User verifies the details match their intent. Taps Confirm. PIN/biometric prompt appears — this is the mandatory human gate before any on-chain action.
Agents CANNOT execute without explicit user confirmation + authentication.
6
TEEPIN verified, Uniswap calldata signed in TEE
Swap calldata (encoded Uniswap exactInputSingle call) is signed in the TEE. Signed transaction returned.
7
Cloud OSTransaction Module broadcasts to Ethereum; AI Agent confirms in chat
Bridge App returns only the signed bytes to the Cloud OS Transaction Module — keys never left the Bridge App TEE. Cloud OS broadcasts to Ethereum via RPC. The AI Agent responds in the Bridge App chat: "Swap submitted! Tx: 0xabc… — I'll notify you on confirmation." Cloud OS WebSocket pushes confirmation when mined.

Permission model: dApps can only access resources the user explicitly grants. Permissions are scoped: wallet:read gives read-only balance access; wallet:sign allows transaction proposals (still require user confirmation each time). No dApp gets blanket signing access.
1
UserOpens dApp Store, filters by category or searches
Store loads from /apps with filters applied. Featured section shown first. Audit status badges visible on each card (Verified / Pending / Unreviewed).
2
UserTaps app card → reviews detail page
Detail page shows: description, screenshots, supported chains, permission list, audit report link, install count, and rating.
3
Cloud OSCloud OS App Module serves permission review sheet to Bridge App
The Cloud OS App Module reads the app's declared permissions from its .w3app manifest and sends a structured permission list to the Bridge App for rendering. User can toggle optional permissions; required ones cannot be deselected.
wallet:read — requiredwallet:sign — optional
4
Cloud OSCloud OS binds app to user's DID — Bridge App downloads native wrapper
Cloud OS App Module records granted permissions and binds the app to the user's DID. The Bridge App downloads the platform-native wrapper binary (.aab / .ipa / .msix). App installs locally on device but is governed globally by the user's DID in the Cloud OS.

1
UserOpens app — locked state shown
App detects existing keystore. Shows welcome back screen with DID display name and biometric/PIN unlock options.
2
Cloud OSBridge App requests challenge from Cloud OS Identity Module
Bridge App sends DID to the Cloud OS Identity Module (/auth/challenge). Cloud OS issues a one-time nonce challenge (5-minute TTL) and stores it in Redis keyed by DID. Authentication begins in the Bridge App — the Cloud OS never holds credentials.
3
TEEBiometric unlocks TEE, challenge signed with DID key
User touches fingerprint / looks at FaceID. OS biometric API unlocks the TEE, which decrypts the signing key and signs the challenge. Signing key never exposed to app process.
4
Cloud OSIdentity Module verifies signature against DID Document public key
Cloud OS Identity Module resolves the DID from its registry, reads the public key from the DID Document, and verifies the signed challenge. On success, issues a JWT (1h) + refresh token (30d) back to the Bridge App. No password. No centralised credential store.
5
UserDashboard loads — fully authenticated
JWT stored in memory (not persisted to disk). WebSocket connection established. Balances loaded. Total flow: under 3 seconds on good network.
No password. No email. No centralised credential store.
