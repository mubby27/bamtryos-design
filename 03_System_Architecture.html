01
Architecture Overview
High-level system topology and design philosophy

BamtryOS is a Hybrid Web3 Operating System built on a two-tier architecture: a local Bridge App that runs natively on the user's device, and a Decentralised Cloud OS that governs identity, permissions, assets, and all coordination logic. The Bridge App handles local execution, cryptographic signing, and device I/O — while the Cloud OS is the permanent, portable, sovereign layer that the user truly owns. The two communicate over an encrypted Secure Session Link. The identity is never owned by the device — only proven by it.

📱
Bridge App (Local Runtime)
The native app installed on mobile or desktop. Renders UI, hosts native app wrappers, executes cryptographic signing, and provides device access (camera, sensors, biometrics). Replaceable — the identity is not.
☁️
Decentralised Cloud OS
The permanent OS runtime in the cloud. Owns the user's DID, wallet, storage, app governance, and global settings. Accessible from any Bridge App on any device — the user's identity travels with them.
🔐
Secure Session Link
End-to-end encrypted channel between the Bridge App and Cloud OS. The cloud never "logs in" the user traditionally — it verifies cryptographic proof that the user controls their DID.
🪪
DID-First Identity
W3C DID Core 1.0 identity lives in the decentralised runtime, not on any device. The same identity works across all devices. Devices are independently authorised and revocable.
📦
.w3app Format
One source package generates native binaries for Android, iOS, Windows, macOS, and Linux. Apps declare permissions, monetisation rules, and chain requirements in a single manifest.
🔗
Multi-Chain Financial Engine
The wallet is not an app — it is an OS-level financial engine. Apps never touch keys or chains directly. All asset operations are mediated by the Cloud OS wallet module.
ℹ️
Core Design Principle: BamtryOS is not "apps in the cloud." It is local software governed by a decentralised operating system. The Bridge App is replaceable. The identity is permanent. Users own their DID, their data (encrypted decentralised storage), and their assets — the OS makes this seamlessly accessible without sacrificing UX quality.

Two-Tier Architecture
Bridge App (local) ↔ Decentralised Cloud OS

BamtryOS is not a cloud app with a mobile front-end. It is a two-tier system where the local Bridge App acts as the trusted execution boundary on the user's device, while the Decentralised Cloud OS is the permanent OS runtime that the user truly owns. The two communicate over an end-to-end encrypted Secure Session Link. Authentication happens locally — the cloud verifies cryptographic proof, never credentials.

03
9 Core Modules
Feature modules of the Decentralised Cloud OS

The Cloud OS is decomposed into 9 independently deployable modules. Each module owns its data, exposes versioned APIs, and can be upgraded without affecting others. Apps interact with modules through the Bridge App mediation layer — never directly.

Module A
Identity & Authentication
The entry point to the OS. Authentication begins in the Bridge App using cryptographic proof (wallet signature, biometric, hardware key). The Cloud OS verifies proof — never passwords. The DID lives here, never on the device.
W3C DID Core 1.0did:ethrdid:bamtryVerifiable Credentials
Module B
Wallet & Asset Engine
Not a wallet app — an OS-level financial engine. Every app on BamtryOS interacts with assets through this module, never directly with blockchains. Manages multi-chain assets, normalises gas, simulates transactions, abstracts chain differences.
EVMSolanaCosmosBitcoinNFTsRWAs
Module C
Transaction & Execution
Turns user intent into deterministic execution. Validates intent, simulates outcomes, estimates fees, handles batching, scheduling, and cross-chain routing. Cryptographic approval happens in the Bridge App TEE; orchestration logic lives here.
Intent validationSimulationCross-chainBatching
Module D
Application Runtime
Governs how apps exist, run, and behave. Apps register with the Bridge App, declare permissions, and the Cloud OS binds them to the user's DID. Enforces sandboxing, permission boundaries, identity-scoped access. Enables remote revocation.
SandboxingPermissionsDID bindingRevocation
Module E
App Store & Distribution
The canonical distribution layer. Developers submit .w3app packages. The store reviews, signs, and distributes platform-native binaries. Manages updates, rollbacks, and revocation. Apps are installed locally but owned globally by the user's DID.
.w3app formatCode signingRollbackRevocation
Module F
Storage & Data
Governs where data lives and who controls it. Local storage is encrypted cache only — the source of truth is always decentralised storage encrypted with keys from the user's DID. Apps get scoped access, not ownership. Cross-device sync is automatic.
IPFSFilecoinAES-256-GCMApp isolation
Module G
Profile & System Settings
Manages the user's presence inside the OS: identity attributes, device authorisation, security preferences, notification behaviour, app permissions. All changes propagate across devices because they are bound to the DID, not the hardware.
Device authSession mgmtRemote logoutRecovery
Module H
Governance & Network
Allows the OS itself to evolve without breaking user trust. Manages protocol upgrades, governance proposals, voting, and emergency interventions. Users participate directly or delegate. Replaces opaque platform governance with cryptographically enforced decisions.
DAOProposalsVotingProtocol upgrades
Module I (Local)
Bridge App
The local embodiment of the OS. Renders UI, handles device I/O, secures cryptographic operations, hosts native app wrappers, enforces permissions, acts as the user's trusted execution boundary. Does not own identity, data, or assets — it is replaceable.
TEE signingBiometricsOffline supportNFC/QR
⚠️
Module boundary rule: Apps never directly access wallets, identity, storage, or device APIs. Every request is mediated through the Bridge App which logs and enforces the permission boundaries defined by the Cloud OS. This is what enables remote revocation and portable app ownership.

05
.w3app Package Format
Custom app format — one source, all platforms

BamtryOS does not accept arbitrary APKs or executables as first-class applications. Developers submit a .w3app package built with the Web3 OS SDK. From one source, the SDK generates native binaries for every supported platform. Apps declare permissions, chain requirements, and monetisation rules in the manifest.

.w3app Package Contents
A single deployable package containing everything the OS needs to install and govern the app.
▸App manifest — permissions, chains, device APIs, monetisation rules
▸Core logic — Web3 OS runtime compatible (WASM / SDK)
▸UI definitions — platform-adaptive layouts
▸Cloud backend bindings — which Cloud OS modules the app uses
▸Cryptographic signature — developer identity and integrity proof
Native Wrapper Generation
From one .w3app, the SDK builds platform-native binaries. Wrappers adapt to the host OS but cannot bypass Web3 OS permissions.

Core Kernel
Cryptographic foundation and device-level primitives
🔑
Secure Keystore
Private keys are generated and stored in hardware-backed secure storage (Android Keystore, iOS Secure Enclave, TPM on desktop). Keys never leave the device in plaintext. All signing operations execute within the TEE boundary.
AES-256-GCMECDSA secp256k1Ed25519TEE
🧮
Crypto Engine
Native cryptographic primitives for hashing, signing, verification, and key derivation. Supports BIP-39/44/84 for HD wallet derivation paths across all integrated chains. Exposes a unified CryptoAPI to upper layers.
BIP-39/44/84SHA-256/3Keccak-256Blake2b
🪪
DID Resolver
W3C DID Core 1.0 compliant resolver supporting did:ethr, did:sol, did:key, and custom did:bamtry method. Resolves DID Documents from IPFS and on-chain registries. Manages verifiable credential issuance and verification.
W3C DID Core 1.0did:ethrdid:solVerifiable Credentials
📡
Local Event Bus
Async publish-subscribe system for intra-device communication between layers. Uses persistent message queues for offline resilience. Events are signed by the kernel to prevent injection from untrusted sources.
Pub/SubMessage QueueSigned EventsOffline-first

04
Protocol Bridge
Unified multi-chain abstraction layer

The Protocol Bridge is the translation layer between BamtryOS's universal API and the heterogeneous world of blockchain protocols. It implements the Adapter Pattern — each blockchain has a dedicated adapter that implements a common IChainAdapter interface. Upper layers interact only with this interface, never with chain-specific libraries directly.

Universal Chain Interface
interface IChainAdapter {
  // Identity
  getAddress(): Promise<string>;
  signMessage(msg: string): Promise<string>;

  // Balances & Tokens
  getBalance(address: string): Promise<BigInt>;
  getTokenBalances(address: string): Promise<TokenBalance[]>;

  // Transactions
  buildTransaction(params: TxParams): Promise<RawTx>;
  signTransaction(tx: RawTx): Promise<SignedTx>;
  broadcastTransaction(tx: SignedTx): Promise<TxHash>;
  getTransactionStatus(hash: TxHash): Promise<TxStatus>;

  // Smart Contracts
  callContract(params: ContractCallParams): Promise<unknown>;
  estimateFee(tx: TxParams): Promise<FeeEstimate>;

  // Subscription
  subscribeToAddress(address: string, cb: EventCallback): Unsubscribe;
}

Security Model
Zero-trust, device-first security architecture
🔐 Key Management
  • Private keys generated on-device using secure RNG
  • Keys stored in TEE (Android Keystore / Secure Enclave / TPM)
  • Keys never transmitted in plaintext — ever
  • Hardware-backed biometric binding (fingerprint/FaceID)
  • BIP-39 12/24-word mnemonic recovery (user-held)
🪪 Identity & Auth
  • DID-based authentication — no username/password server
  • Challenge-response sign-in (wallet signature challenge)
  • Session tokens are DID-signed JWTs with short expiry
  • Device revocation propagated to all DID document controllers
  • Verifiable Credentials for selective disclosure
📦 Data & Storage
  • All IPFS uploads encrypted with user's public key (AES-256-GCM)
  • Encryption keys derived from DID key material
  • CID access control list stored on-chain
  • Local data encrypted at rest (SQLCipher / DPAPI)
  • No PII stored on Bamtry servers
🛡️ Transaction Safety
  • All transactions require PIN/biometric confirmation
  • AI Transaction Agent screens for phishing/anomalies
  • Spending limits configurable per chain and per dApp
  • dApp permission model (camera, contacts, sign, etc.)
  • Transaction simulation before broadcast (fork-based preview)
🔒 Transport Security
  • TLS 1.3 enforced on all API endpoints
  • Certificate pinning on mobile clients
  • HSTS + CSP headers on all web surfaces
  • All WebSocket connections authenticated via DID token
🧪 Auditing
  • Smart contract audits required before dApp Store listing
  • OWASP ASVS Level 2 compliance target
  • Penetration testing before mainnet launch
  • Bug bounty program via Immunefi post-launch
  • Immutable on-chain audit trail for all signed actions
